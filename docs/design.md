# 設計理念與踩過的坑

這份是「為什麼是這樣做」的記錄。只想用工具的話不需要看這份。

---

## 為什麼是兩支獨立的工具

| | **resetter**（ClaudeTimerResetter.exe） | **resumer**（ClaudeResumer.exe） |
|---|---|---|
| 立場 | **主動排重置**：我去把重置時鐘催起來 | **已知重置點、準時送**：我已經知道幾點會恢復 |
| 做幾次 | 反覆做同一件便宜的事 | 一次性，送完就關 |
| 時間點是誰決定的 | 程式**算出來**的（提前量、視窗週期） | **人**判斷的（Claude 告訴你的重置時間） |
| 該不該查用量 | **該**。看用量、算時間、決定打不打，是它的本分 | **不該**。你設的時間就是最終決定，不做二次確認 |
| 時間到做什麼 | 查用量 → 視窗還沒開就打探針、快重置就等一下再打 | 直接把那個對話接著送出去，就這樣 |
| 常駐嗎 | 是（排程或工具列） | 否 |

兩者要解決的問題不一樣，所以刻意做成兩支獨立的 exe，而不是一個工具的兩個分頁。

**早期版本踩過的坑**：把 resetter 那套「查用量、看有沒有重置、沒重置就壓著等」塞進了
resumer，結果是「Claude 說某點重置、resumer 卻自己算出還要 4 小時、於是把你排好的任務
壓著不送」。那是把兩支工具的職責搞混了——現在 resumer 已經沒有任何用量閘門，時間到就送。

---

## 為什麼排程規則要能填任意時間點

Claude 的用量視窗有固定週期（5 小時），但重度工作常常 2~3 小時就把額度用完。照平常
習慣、坐到位子上才開始用，額度用到一半就會撞牆，只能乾等視窗重置，正好卡在最需要它
的時候。

比較好的做法是反過來：在預期會重度使用「之前」，先用探針提前把重置時鐘啟動。這樣等
真正進入重度工作、額度快用完的時間點，剛好又迎來下一輪重置。

所以每一次觸發時間點的意義是「**預估到這個時候額度差不多要用完了，該催下一輪重置**」，
**而不是**「這個時間點才開始工作」——這兩者常常對不上，尤其實際到工位的時間本身就有
彈性，觸發時間需要抓提前量，不能卡在表定時間本身。

這就是 `daily_times` 規則直接支援任意時間點清單（而不是把使用者鎖死在「每隔 N 分鐘」）
的理由。兩個帳號會在各自的機器上各自安裝一份，排程互不影響。

## 為什麼那一次探針這麼便宜

| 項目 | 設定 | 理由 |
|---|---|---|
| 模型 | `claude-haiku-4-5-20251001` | 目前最便宜的一檔 |
| 工具 | 全關 `tools=""` | 純文字進出；開工具是 agent 模式，貴 15~45 倍 |
| thinking | `MAX_THINKING_TOKENS=0` | 回一個 "k" 不需要模型多想 |
| 權限 | `manual` | 工具全關，這裡只是明確表態不自動放行 |
| session | `persist=False` | 不保存、不重送歷史（重送歷史才是最貴的） |
| 提示 | system `Reply with exactly: k` ＋ prompt `k` | 重點不是提示多短，是回覆多短 |

**實測 $0.000254，約 4 秒。**

### 真正省到錢的那一步：讓它別多話

haiku 的 output 單價是 input 的 5 倍，所以把提示從 `hi` 縮到 `k` 其實幫不上忙，真正貴
的是模型回了一整句寒暄。實測同一台電腦、連續兩次：

| 組合 | input | output | 單次 |
|---|---|---|---|
| 舊：system 一句中文＋prompt `hi` | 263 | 23 | $0.000378 |
| 新：system `Reply with exactly: k`＋prompt `k` | 234 | 4 | $0.000254 |

**省 33%。** 兩件事一起做的：系統提示從中文換英文（同意思的英文 token 比較少），
以及明講「只回 k」把 output 從 23 個 token 壓到 4 個。

## 排程為什麼不是用 sleep 等

Task Scheduler 那個工作有 `ExecutionTimeLimit` PT5M，單次 tick 卡在 sleep 裡等 15 分鐘
會被系統砍掉。所以 `--tick` 跟工具列常駐都用 `ping.refresh(max_wait_seconds=0)`：
ping 回報 `waiting` 時，呼叫端用 `rules.rollback()` 把這條規則的觸發還原，讓下一輪 tick
重新判定一次。

等於用既有的 tick 節奏做「時間到再確認一次」，語意跟原地等一樣，但不會被砍。手動在
命令列跑 `test.bat` 則預設允許原地等（最多 15 分鐘多一點）。

規則狀態也是先存檔再打探針：就算探針途中當機，下次 tick 也不會把同一次觸發重打一次。

## 用量端點的限制

`usage.py` 讀的 `GET /api/oauth/usage` **不是公開文件化的 API**，是 Claude Code 內部
用的。欄位名稱可能會變，所以只挑 `five_hour` / `seven_day` 兩個欄位，其他一律當作
不存在。token 過期會回結束碼 3；開一次 Claude Code 它就會自動換新。

對計時器最有用的一個欄位是 `five_hour.resets_at` 是不是 `null`——`null` 代表這個 5 小時
視窗**還沒被任何一次呼叫開啟**。`usage.py --json` 把這件事直接給成 `window_open` 布林值。

## resumer 早期為什麼「時間到了但什麼都沒發生」

第一版是 fire-and-forget，而且錯在幾個地方剛好都不會出聲——`--windowed` 打包沒有主控台，
例外訊息無處可去。修掉的是：

| 問題 | 後果 | 現在 |
|---|---|---|
| 沒給子行程 `cwd` | Claude Code 的對話是**按專案目錄**存的，在別的目錄下 `--resume` 那個 id 會直接找不到對話 | 一律在該對話的 `cwd` 底下執行 |
| 沒給 `stdin` | `DETACHED_PROCESS` 之下沒有主控台，繼承來的 stdin 是無效 handle | `stdin=DEVNULL` |
| `Popen` 一成功就標「已送出」 | 行程起得來不代表事情有做成；`session 已被佔用`、`找不到這個 session` 都是起得來但秒退 | 盯 60 秒，秒退就標失敗並印出紀錄尾巴 |
| 例外沒有人接 | 找不到執行檔、套件沒裝等等全部靜靜消失在 Tk 的 callback 裡 | 全部接起來寫進畫面的「狀況 / 錯誤」欄與 `resumer.log` |
| 送出後 2 秒就自動關閉 | 就算有錯誤訊息也來不及看到 | 只有全部確認送出才自動關，而且可以取消勾選；有失敗一律留著 |
| 時間到還去查用量、沒重置就壓著等 | 明明時間到了卻不送 | 整段用量閘門移除，時間到直接送 |
| 對話正開在 VSCode 裡才發現被鎖 | 白送一次、還不知道為什麼 | 送出前零成本偵測，被佔用就擋下並在你關掉後自動補送 |

## v1.1.0 修掉的三件事

**畫面下半看不到**：視窗尺寸寫死 1140x970、最小尺寸 960x840，遇到 1366x768 或
1536x864 的螢幕就直接比螢幕還高，下面的佇列跟錯誤訊息**沒有任何辦法看到**。現在
(1) 開啟時自動貼合螢幕可用空間、(2) 最小尺寸放寬到 720x520、(3) 整個版面放進可捲動
容器（`ui/scroll.py`），內容超過高度就出現捲軸，沒超過就自動收起來。

**對話預覽是一長串字串**：一個做了三小時的對話，九成記錄是工具往返跟 thinking，原封
不動接成一大段字串等於什麼都沒說。現在 `resumer/transcript.py` 會分類（人講的 / Claude
回的 / 工具 / 思考 / 壓縮點）、把連續工具呼叫併成一行、照時間切段、算出摘要；
`resumer/viewer.py` 用摘要卡 + 時段大綱 + 可摺疊訊息呈現，另外有搜尋跟顯示開關。

**一份 README 塞所有東西**：29 KB 的單一檔案，安裝跟接續功能的說明混在一起。現在拆成
README（入口）＋ `docs/resetter.md`、`docs/resumer.md`、`docs/build.md`、`docs/design.md`，
GUI 裡的說明文字也重寫過（每個選項旁邊直接寫清楚它是什麼、什麼時候用）。
